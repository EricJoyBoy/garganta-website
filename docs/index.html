GARGANTA / DOCUMENTATION

Make yourself at home.

A practical guide to your local workspace, from the first setup to reviewing a change.

Alpha guide · 0.1.0a1
Website demo or real workspace?

The interactive demo runs entirely in your browser with synthetic data. The application runs locally and needs an installed, authenticated Kiro CLI to execute agents. Its source repository is currently private.

01 / START SMALL

Getting started

Begin with a small local repository or the included sample project. Jira is optional for the local chat path.

Requirements

  • Python 3.12 or later and Git.
  • macOS or Linux. Windows developers can use WSL; cross-platform pilot testing is still pending.
  • A separately installed and authenticated Kiro CLI for agent execution.
  • Collaborator access to the private application repository.

Node and npm are needed to rebuild the frontend. The current preparation includes compiled interface assets.

Install and start

git clone https://github.com/EricJoyBoy/garganta.git
cd garganta
./start-dashboard.sh

Open http://127.0.0.1:7655/setup/start. The launcher creates a Python virtual environment and installs the application's web dependencies when needed.

Complete the setup wizard

  1. Select a local repository, or choose examples/local-project for a synthetic example.
  2. Leave Jira fields empty to start with local chat.
  3. Review and save the configuration, then follow any restart instruction shown by the application.
  4. Open Chat and choose Developer or Tech Specialist.

The wizard does not install Kiro, sign you in to connected services or install a team's private agents and runtime hooks.

Need access? Use “Meet the builder” in the top bar to contact the project author. The public website repository contains only this site, not the application.

02 / YOUR WORKSPACE

Configuration

Personal configuration, work history and team profiles have separate roles. Keep credentials and organization-specific settings outside the source repository.

Configuration locations and overrides
SettingDefault / behavior
Personal configuration~/.garganta/launcher-config.json
GARGANTA_HOMEChoose another configuration directory.
GARGANTA_DATA_DIRChoose a separate directory for application-owned history and state.
Team catalogAn external TOML catalog, selected during setup when needed.
Service inventory~/.garganta/integrations.json, or the file selected by GARGANTA_INVENTORY.

No previous installation is migrated automatically. For an isolated test installation, choose new configuration and data directories before starting:

export GARGANTA_HOME="$HOME/.garganta-demo"
export GARGANTA_DATA_DIR="$HOME/.garganta-demo-data"
./start-dashboard.sh

Use the same directory settings when restarting that installation.

03 / WORK WITH AN AGENT

Chat & agents

Choose Developer or Tech Specialist and ask about the selected repository. If matching custom agent definitions are absent, local chat uses Kiro's default agent with the selected role instructions.

A useful first request

Explain this repository's entry points and suggest a small improvement. Read the relevant files first and tell me which sources support your answer.

The project files available to the agent are the files on the machine where Garganta and Kiro run. A remote environment does not automatically gain access to repositories or credentials on your laptop.

Tool permissions

Permissions depend on your Kiro runtime and agent configuration. Agents operate with your user privileges and may read files, change code or invoke tools when permitted.

This alpha does not provide a complete approval dialog for every ACP request. A request requiring client approval stops the turn by default. Automatic approval is an explicit opt-in through GARGANTA_AUTO_APPROVE_TOOLS=1; it is not a prerequisite for reading this guide or exploring the demo.

A disconnected or interrupted turn is not automatically replayed. Check its recorded activity before deciding to retry.

04 / INSPECT THE RESULT

Review & evidence

A completed run and a verified change are different things. A model's statement that tests passed is not a test report.

  1. Read the intended change. Check the requirement and acceptance criteria against the issue.
  2. Inspect the selected version. Read the code diff or document version, including the base and final commit or document hash when available.
  3. Open the evidence. Check recorded reports, their scope and which version they apply to.
  4. Recheck after changes. When the inputs or code change, earlier results may no longer support the new version.
  5. Make a decision. Note missing evidence and unresolved questions before accepting the work.
How to read the website demo

DEMO-42, its code excerpts, timings and reports are fictional. “Mark as reviewed” and “Complete sample review” change only the browser's temporary demo state. They do not approve a real change or perform a merge, push or deployment.

Review modules in the retained alpha source need their corresponding profiles and configuration. The initial pilot path focuses on local setup and chat.

05 / CONNECT WHAT YOU NEED

Optional integrations

You can start without external delivery services. Add integrations only when their workflows are configured and you can verify the intended access.

Jira

Issue workflows can be supplied through an external team catalog such as launcher.toml. Jira credentials are personal. The local chat setup can leave Jira unset.

Jenkins & AWS

These modules need configured credentials, inventories and relevant workflow profiles. The generic source includes no organization pipeline catalog or cloud account.

Copy examples/integrations.json to your personal configuration directory and populate only the resources you intend to use. Inventories are empty by default.

Configured Jira, Jenkins and AWS paths still need end-to-end testing in your own environment. Their presence in the source is not a claim that a particular deployment has been validated.

06 / FIND YOUR NEXT STEP

Troubleshooting

The application repository returns “Not found”

The application is a private alpha. Confirm that the GitHub account used by Git has collaborator access. Access to this public website does not grant access to the application.

The interface opens but the agent cannot run

Check that Kiro is installed and authenticated on the same machine, and that the selected agent configuration and its referenced prompt files exist. Setup does not install or authenticate Kiro.

A tool needs approval or a turn stops

Read the recorded tool outcome and inspect the Kiro permission policy. Do not assume an interrupted call succeeded or retry operations with uncertain external effects without checking their actual result.

Can I use another local port?

Pass the desired port to the launcher, for example ./start-dashboard.sh 7656. Open the corresponding local URL.

Can I run the Python application on GitHub Pages?

No. Pages serves this static website and browser-local demo. Running Garganta requires a Python environment and an agent runtime. The public website is separate from the application.

07 / CURRENT SCOPE

Alpha status

Garganta is a local, single-user application under preparation for a public source release. Keep the application server local; this release is not a hosted multi-user service.

  • Local setup and chat are the initial pilot path.
  • Cross-platform and real-runtime testing remain in progress.
  • Retained workflow, review, KB and delivery modules need their corresponding configuration and further integration checks.
  • Model requests and connected-service data may leave the device.
  • The application's top-level source license and provenance review remain pending.

The website and its sample-data demo are public. The application's source repository remains private.
